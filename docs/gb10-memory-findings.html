The missing DRAM counter

Every NVIDIA profiling guide reads memory traffic from dram__bytes.sum. On GB10 that counter does not exist — and neither does any other dram__* metric. Here is what replaces it, the experiment that proves it, and what it measured.

The problem

There is no separate memory to count

Enumerating GB20B's metric namespace turns up 5,292 counters across twelve prefixes — lts__, smsp__, l1tex__, sm__ and nine more. There is no dram__. There is no fbpa__. There is no ctc__ either: the NVLink-C2C counters a Grace-Hopper part exposes are absent, and Nsight Compute's C2CLink section is gated to CC_90 and CC_100, so it never applies to a CC_121 part.

That is not an oversight. This GPU has no private VRAM — it shares one coherent LPDDR5X pool with the Grace CPU. There is no separate device memory to put a counter on.

What does exist is L2's aperture breakdown. Every access that misses L2 is tagged with where it went: device for private VRAM, sysmem for host-coherent memory, peer for another GPU. On an integrated part, everything past L2 is sysmem.

The substitution

One counter, proven against a known quantity

The claim is that lts__t_sectors_aperture_sysmem_lookup_miss × 32 B is the traffic reaching LPDDR5X. Everything downstream rests on it, so it is not taken on faith — it is checked against an amount of traffic we already know.

The test allocates two 256 MiB fp32 arrays and runs an elementwise multiply. That kernel reads 256 MiB and writes 256 MiB, so exactly 536.9 MB must cross the memory interface:

# one elementwise multiply over 2 × 256 MiB fp32
lts__t_sectors_aperture_sysmem_lookup_miss  16,780,246 sectors
                             × 32 B  =      537.0 MB   ← expected 536.9 MB

lts__t_sectors_aperture_device_lookup_miss           0   ← sentinel
lts__t_sectors_aperture_peer_lookup_miss             0   ← sentinel

Calibration gate · passed

An error of +0.02%, with both sentinel apertures reading zero as they must on a part with no private VRAM. This runs before every benchmark, and the result is stamped into the run manifest — so a report always says which regime its numbers came from.

The sentinels matter as much as the match. If a driver update ever starts routing traffic through the device aperture, this derivation silently halves. Checking turns that into a loud failure instead of a quiet wrong answer.

Physics check · consistent

A decode step must read every weight and the whole KV cache to emit one token, so its traffic is predictable from first principles: 1.19 GB of resident weights plus 62 MB of KV cache. Measured: 1.44 GB — 1.15× predicted, the remainder being activations and workspace.

Against the checkpoint's 1.50 GB on disk, that is 0.96× the model per token. Two independent runs agreed to within 0.3% on every figure here.

The gap is 9.3× in arithmetic intensity. Both phases sit below the 411 FLOP/B ridge — decode by a factor of 35 — which is the structural reason decode cannot be made fast by better arithmetic. The lever is bytes moved, not FLOPs.

Why, not just how much

Decode is memory-latency bound, and short of warps

Bytes say how much work the memory system did. They cannot say why a kernel took the time it did — and decode runs at only 38% of the achievable rate, so it is not simply out of bandwidth.

For every cycle a warp could have issued and did not, the hardware records why. Weighted by each kernel's true share of GPU time:

Limiter · latency, not bandwidth

Mean achieved occupancy across decode is 25%, and several kernels run at under 0.01 waves per SM — they cannot fill the machine once, let alone keep enough requests in flight to hide memory latency. The elementwise and normalisation kernels between the GEMMs are individually tiny and collectively expensive.

On this workload, fusing or enlarging those kernels would buy more than moving fewer bytes would. That conclusion is only reachable because the bytes and the stall reasons were measured together.

Method

What makes these numbers usable

  • Timing comes from an unprofiled run. Nsight Compute replays every kernel; a decode step measured under it takes far longer than it really does. The reported 15.7 ms per token and 63.9 tok/s come from a separate pass with no profiler attached.
  • One decode step is profiled, not all of them. The kernel mix does not change between tokens, so a single NVTX-scoped step yields every unique kernel — all 1,618 launches of it — at a fraction of the cost. The step chosen is the last, where the KV cache is deepest.
  • Hit rates are recomputed from raw counts, never averaged across kernels. Averaging percentages would weight a microsecond elementwise kernel the same as a GEMM moving hundreds of megabytes.
  • L2 hit rates are a lower bound. Caches are flushed between replay passes so each kernel is measured independently of what ran before it; a real decode loop may carry data across steps.
  • Footprint comes from three sources — the torch allocator, cudaMemGetInfo, and /proc/meminfo — because NVML reports GPU memory as N/A on this part. They are not interchangeable: on a unified-memory part cudaMemGetInfo covers the whole shared pool, so its figure counts every other process on the machine and is not this run’s footprint. The per-process draw is the 1.90 GB the host pool lost while loading weights, against 1.63 GB reserved by the allocator.
  • Bandwidth figures are upper bounds. Byte counts come from a profiled pass with L2 flushed before every replay, so they exclude the cross-kernel reuse a real run gets. Dividing them by unprofiled wall time exceeds this machine’s own measured ceiling for prefill — proof that the numerator reads high, and the reason no such figure here is quoted as an achieved rate.
  • The GPU is not busy for the whole phase. A decode step spends 35% of its wall time with no kernel running — launch latency across 1,618 dispatches, not memory and not compute. Every bandwidth and utilisation figure divides by kernel time, so all of them describe the busy fraction only.

Running it

Four commands

# what can this machine measure? (probes real collections, not the metric list)
nsbench preflight

# turn a .safetensors checkpoint into a config
nsbench discover /path/to/checkpoint --name my-model

# calibrate, time, trace, profile, report
nsbench run --model configs/models/my-model.yaml \
            --workload configs/workloads/decode-focused.yaml

# put runs side by side, normalised per token
nsbench compare runs/*__sweep

Budget roughly a minute of Nsight Compute per 100 kernels in scope. An eager transformers decode step runs about 58 kernel launches per transformer block, so a 28-layer model is ~1,600 launches, or ~16 minutes per phase. --skip-ncu gives the timeline and honest timing in minutes instead.
